# Context

Discovery work is hypothesis-driven: generate candidate approaches,
prototype them when practical, evaluate against criteria, kill the weak,
and put the survivors in front of a human — possibly over days, across
daemon restarts, and without an evaluator quietly moving the goalposts
mid-experiment (mission §13–§16). Nothing in v1 models this.

# Decision

1. **Experiments are definitions; rubrics are pinned before evaluation.**
   An `ExperimentDefinition` (candidate count, generation strategy,
   prototype flag, survivor count, `maxIterations`, optional wall-clock
   and budget limits) references an `EvaluationRubric` by name; both are
   versioned definitions resolved into the run's snapshot (ADR-0018), so
   the criteria that judge a candidate are fixed at experiment start.
   The evaluator scores the pinned criteria verbatim (0–10 each);
   `weightedScore` is computed by the engine from declared weights,
   never by the model.
2. **Kill criteria are expressions where possible, evidence otherwise.**
   A kill criterion with an `expression` is engine-evaluated with the
   workflow scope-expression language against a documented candidate
   scope (per-criterion scores, weighted score, evidence/artifact
   counts, raw evaluator outputs). Expression-less criteria are placed
   in the evaluator prompt verbatim and honored only via structured
   `kills` outputs matching the rubric. Candidates below the rubric's
   `advanceThreshold` are killed by the engine. A failed prototype kills
   the candidate, never the experiment, and leaves a lesson.
3. **The runner is a resumable reducer.** `ExperimentRunner.step` derives
   the phase from the persisted `ExperimentRecord` alone — generate →
   prototype (when declared) → evaluate → select → awaiting-judgment —
   executes exactly one phase, persists, and returns. No in-memory state
   survives between calls, so the machine survives restarts and JSON
   round-trips (ADR-0017 tick model applied to experiments).
4. **Human judgment is a durable wait carrying a JudgmentPackage.** When
   survivors exist the record enters `awaiting-judgment` and the graph's
   experiment node suspends as a durable wait (ADR-0019). The package is
   compact and decision-shaped: hypothesis, rubric summary, kill
   criteria, ranked survivors with key evidence and artifacts, a
   recommendation, aggregated risks, and iteration position. The
   decision is a closed set — `kill`, `advance` (optionally selecting a
   candidate), `iterate`, `need-more-evidence` — persisted as a
   `JudgmentOutcome` with responder and time for judgment observability.
5. **Iteration is bounded.** `iterate` past `maxIterations`, a spent
   wall clock, or a no-survivor final iteration concludes the experiment
   as `exhausted`; `need-more-evidence` runs at most one extra evaluator
   pass per iteration. Lessons accumulate on the record and feed the
   next iteration's generation context.

# Rationale

- Pinning the rubric before evaluation is what makes scores comparable
  across candidates and iterations; rubric improvement happens through
  new versions with explicit approval (ADR-0018), not mid-experiment.
- Engine-computed weighted scores and engine-evaluated kill expressions
  keep the model's role to producing evidence and per-criterion
  judgments — the aggregation and the kill decision are auditable
  arithmetic.
- A compact JudgmentPackage respects the human's position as the scarce
  resource: the decision needs the evidence that matters, not the full
  transcript (which stays reachable via artifacts and the record).

# Alternatives Considered

- **Letting the evaluator conclude experiments autonomously** — removes
  exactly the judgment the primitive exists to elicit; rejected: humans
  decide kill/advance, the machine decides only what a declared
  expression or threshold already decided.
- **A long-lived experiment process orchestrating all phases** — dies
  with the daemon; rejected for the reducer (same reasoning as
  ADR-0017).
- **Unbounded iterate-on-request** — a polite infinite loop; rejected:
  `maxIterations` is part of the definition and exhaustion is an honest
  terminal conclusion.
- **Free-text judgment decisions** — unparseable for observability and
  resumption; rejected for the closed decision set plus free-text
  feedback.

# Consequences

- Positive: experiments suspend for days awaiting judgment at zero cost;
  every kill has a recorded criterion and reason; judgment outcomes
  accumulate into an observable decision history per period.
- Negative: the scope-expression language has no ordered comparisons, so
  numeric kill rules must be phrased as evaluator-emitted boolean
  outputs; one evidence pass per iteration may feel restrictive but
  keeps `need-more-evidence` from becoming the unbounded loop.
- Evaluator and generator outputs are strictly validated (unknown
  criteria, malformed candidates fail the step as corrupt responses) —
  noisy models fail loudly rather than corrupting records.

# Implementation Notes

- Types in `@overture/core` (experiments.ts: rubric, candidate, record,
  judgment, `weightedScore`); reducer in `@overture/experiments`
  (runner.ts); persistence via `ExperimentRepository` /
  `JudgmentRepository` in `@overture/persistence`; the graph experiment
  node binds the runner through an `ExperimentStepper` port and maps
  `awaiting-judgment` onto a WaitCondition (node-executors.ts).
- Evaluator-reported risks persist as prefixed evidence entries and are
  lifted back into the package's risk list (record schema stays flat).
