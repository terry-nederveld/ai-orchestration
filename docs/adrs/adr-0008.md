# Context

Workflow behavior must be user-configurable, versionable alongside a
repository, validating, and executable deterministically. Steps span agent
goals, shell commands, registered actions, and human approvals, with
dependencies, conditions, retries, timeouts, and failure remediation.

# Decision

Workflows are YAML documents (repo-level file `.overture/workflow.yaml`,
plus user/built-in directories) parsed with zod validation into a typed
`WorkflowDefinition`. Step kind is inferred from the discriminating key
(`agent:` / `command:` / `action:` / `approval:`). A pure engine executes the
DAG: steps run when dependencies settle, concurrently up to a cap; `when`
expressions (a tiny safe language: step status refs, outputs, vars, boolean
and equality operators — no eval) are the entire eligibility rule when
present; `${{ … }}` interpolation is resolved engine-side at execution time.
The engine never performs work — all step kinds delegate to injected
executors.

Overall status uses the tainted-skip rule: a step failing without
`continue_on_failure` taints its skipped dependents transitively; the
workflow fails iff a terminal step failed or was skipped-and-tainted.
Benign `when: false` skips (e.g. a declined approval gate) do not fail the
workflow. Remediation forgiveness is explicit in definitions:
`when: steps.review.succeeded || steps.re_review.succeeded` routes delivery
through whichever validation passed.

# Rationale

- YAML + JSON-Schema (generated from zod) gives human-authorable,
  editor-assisted, versionable workflow definitions.
- Inferred step kinds keep documents terse without a redundant `type` field.
- A tiny expression language (tokenizer + recursive descent, no eval) is
  auditable and safe against injection from work-item content.
- The tainted-skip rule was adopted after integration testing showed the
  naive "terminal steps succeeded-or-skipped" rule reported mid-workflow
  failures as success.

# Alternatives Considered

- **Code-defined workflows (TS files)** — maximal power, but not safely
  editable in a UI, not sandboxable, and versioning becomes a code-review
  problem for non-developers; rejected for v1 (extensions can still
  contribute actions in code).
- **BPMN or a full workflow product (Temporal)** — vastly more machinery
  than needed; conflicts with the small-core principle.
- **Implicit remediation forgiveness (a failed step is forgiven when a
  `when`-conditioned step consumed the failure)** — clever but invisible;
  explicit `when` disjunctions were chosen instead.

# Consequences

- Positive: workflows are validated before execution (unique ids, resolvable
  deps, acyclic graph, parseable expressions); dry-runnable against fakes.
- Negative: expressiveness is bounded (no loops beyond retry counts, no
  dynamic step generation) — accepted; loops-with-safeguards arrive via
  retry policies and explicit re-validation steps.

# Implementation Notes

- packages/workflow: schema.ts, parser.ts, expressions.ts, engine.ts,
  providers.ts, builtin-workflows.ts (default software-development flow:
  analyze → implement → test → review → remediate-on-failure → re-review →
  approval gate → PR delivery).
