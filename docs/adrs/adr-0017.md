# Context

Phase 2 generalizes Overture beyond linear coding pipelines: workflows must
express loops, fan-out/fan-in joins, durable waits lasting days, human
input as first-class state, and domain-specific states — while remaining
deterministic (agents reason inside nodes; they never rewrite the graph).
The v1 engine (ADR-0008) is an in-memory DAG executor: it cannot resume a
run mid-flight after a process restart, conflates "where the run is in the
workflow" with "what lifecycle state the run is in", and has no notion of
user-defined domain state or configurable external projection.

# Decision

1. **Graph model.** A workflow is a directed graph of typed nodes (agent,
   command, action, gate, human-input, wait, subworkflow, experiment,
   fan-out, join, terminal) and *declared transitions*. Each transition
   carries an optional condition expression over structured node outputs
   and domain state. Cycles are legal only when every transition entering
   a cycle declares loop bounds (max traversals); the engine enforces the
   bound and fails the run rather than looping unboundedly. The graph is
   immutable for a running workflow version: agent nodes return typed
   structured outputs, and the engine — never the model — selects among
   declared outgoing transitions.
2. **Durable tick execution.** The engine is a resumable reducer, not a
   long-lived promise tree. All execution state — active node executions,
   node results (structured outputs), join progress, loop counters,
   pending waits, domain state — is persisted after every node settlement.
   A tick loads persisted state, executes ready nodes, persists, and
   returns; a run can therefore suspend for days, survive process
   restarts, and resume idempotently from its exact graph position.
3. **Four state layers, kept separate:**
   - *Graph position*: which nodes are settled/active/pending (engine
     bookkeeping, persisted per run).
   - *Engine lifecycle state*: the reserved closed set — QUEUED,
     PREPARING, RUNNING, WAITING, WAITING_FOR_HUMAN, BLOCKED, VERIFYING,
     FAILED, COMPLETED, CANCELLED — extending the v1 run state machine
     with a generic WAITING (ADR-0004 remains the transition authority).
   - *Domain state*: an open, user-defined string plus data bag, set only
     by declared transition effects and lifecycle actions, never by the
     engine's own semantics.
   - *External work-item state*: a configurable **projection** of the
     other layers onto provider mechanisms (status, labels, fields,
     comments). Internal state is authoritative; projection failures
     never corrupt a run.
4. **Compatibility.** The v1 step-DAG YAML (ADR-0008) compiles into this
   graph: steps become nodes, `depends_on` becomes transitions into an
   all-join, `when` becomes transition conditions, tainted-skip semantics
   are preserved by the compiler. Existing workflows keep working; the
   graph is the single execution model underneath.

# Rationale

- Durable ticks are the only design that makes days-long waits, process
  restarts, and disposable model sessions an invariant rather than an
  accident — the v1 recovery behavior (mark interrupted runs Failed) is
  exactly the gap this closes.
- Declared transitions with engine-evaluated conditions keep execution
  deterministic and auditable while still letting models contribute
  judgment through structured outputs.
- Separating domain state from lifecycle state lets users model arbitrary
  processes without widening the reserved set, and the projection layer
  formalizes what v1 hard-coded as success/failure/blocked targets.

# Alternatives Considered

- **FSM-only design** — cannot express fan-out/fan-in or concurrent
  branches without state explosion; rejected by requirement.
- **Retrofit resumability onto the v1 promise-based engine** — resuming
  arbitrary in-flight promise trees requires exactly the persisted
  node-settlement model proposed here; the retrofit is the rewrite.
- **Adopt an external durable-workflow product (e.g. Temporal)** — brings
  its own server, SDK model, and operational burden into a local-first
  desktop product; conflicts with ADR-0011 and the small-core principle.
- **Letting agents modify the graph mid-run** — destroys determinism,
  auditability, and Evaluate; explicitly rejected by the product rules.

# Consequences

- Positive: durable suspension becomes structural; every judgment the
  engine makes (transition chosen, join satisfied, loop bounded) is a
  persisted, explainable record — which is also what the designer's
  Evaluate mode and the run timeline need.
- Negative: two execution models exist during migration (the v1 engine
  remains until its consumers move to compiled graphs); the compiler must
  faithfully preserve v1 semantics, proven by running the existing v1
  engine test expectations against compiled graphs.
- The v1 in-memory engine is deprecated for orchestration once the
  coordinator drives the graph engine; it survives only as the compiler's
  semantic reference until removal.

# Implementation Notes

- Graph model and state-layer types in `@overture/core` (graph.ts,
  run-graph.ts); durable engine in `@overture/workflow` (graph-engine);
  v1 compiler in `@overture/workflow` (compile.ts); persistence in
  `@overture/persistence` (run-graph-state repository).
- Node executors remain injected ports — the engine still performs no
  work itself (ADR-0008 principle carried forward).
