# Context

The v1 desktop app is bound to exactly one runtime: the Tauri shell
spawns the local daemon as a sidecar and hands the webview one
`{ baseUrl, token }` connection to its loopback control plane
(ADR-0011/0012; packages/server binds 127.0.0.1, bearer-token auth,
SSE event stream). Real usage spans more than one runtime — a laptop
daemon, a workstation at the office, a team runtime reachable over
HTTPS — each with its own work sources, runs, and secrets. The v1 UI is
also dashboard-first, organized around the runtime's internals rather
than the user's work.

# Decision

1. **The desktop app is a stateless federation client.** It holds a
   configured set of runtime connections — the local sidecar daemon plus
   any number of remote runtimes over HTTPS — each with independent
   authentication (per-runtime token) and independent availability.
   The app owns no orchestration state: every fact on screen is fetched
   from, or streamed by, some runtime, and every action is a request to
   the runtime that owns the entity.
2. **No central server.** Federation happens client-side: the app
   queries each connected runtime through the same control-plane API the
   single-runtime UI already uses and merges results in the client.
   Runtimes remain unaware of each other; there is no aggregation tier,
   no shared database, and no cross-runtime identity beyond the
   client's own connection list.
3. **The primary surface is work-centric and newest-first.** The home
   view is a single activity feed of work — runs, waits, judgments,
   items needing a human — aggregated across all connected runtimes and
   ordered by recency, with the owning runtime as an attribute of each
   entry rather than the navigation root. Per-runtime drill-down
   remains, but it is secondary.
4. **Offline runtimes degrade to stale cache, visibly.** The client
   keeps the last-known state per runtime; when a runtime is
   unreachable its entries stay in the feed marked stale with their
   last-sync time, and actions on them are disabled. An unreachable
   runtime never blocks rendering the others, and reconnection
   reconciles by refetching — the cache is a display convenience, never
   a source of truth.

# Rationale

- Client-side federation preserves the v1 trust topology: each runtime
  keeps its own loopback-or-HTTPS boundary and token, and compromising
  the aggregate view compromises no runtime. A central server would
  reintroduce exactly the operational and security burden ADR-0011
  rejected.
- Users think in work ("what needs me, what moved"), not in runtimes; a
  newest-first feed makes multi-runtime activity legible without asking
  where anything ran. This follows the agent-UX research findings for
  phase 2.
- Stateless-client-plus-stale-cache is the only consistency model that
  is honest over N independently-available sources; anything stronger
  requires the central server we declined.

# Alternatives Considered

- **A central aggregation service** — single point of failure, a new
  auth domain, and state outside any runtime's boundary; rejected.
- **Runtime-to-runtime mesh federation** — makes every runtime a
  network peer with discovery and trust problems the product does not
  need; rejected.
- **Runtime-first navigation (v1 model, N times)** — forces the user to
  poll each runtime's dashboard mentally; rejected as the primary
  surface, kept as drill-down.
- **Hiding offline runtimes' entries** — silently shrinking the feed
  misrepresents reality; rejected for visible staleness.

# Consequences

- Positive: adding a runtime is configuration, not infrastructure; the
  blast radius of a lost laptop or leaked token stays one runtime; the
  UI degrades gracefully per-connection.
- Negative: cross-runtime queries are fan-out with client-side merge —
  sorting, filtering, and pagination over N sources are bounded by the
  slowest reachable runtime and must be engineered in the client;
  global search across runtimes is approximate while any source is
  stale.
- Each runtime's SSE stream is a separate connection the client must
  multiplex and back off independently.

# Implementation Notes

- The control-plane API (`@overture/server`: bearer-token HTTP + SSE on
  loopback; remote runtimes front the same API over HTTPS) is the
  federation contract — the UI gains no privileged channel. The React
  SPA (apps/desktop/ui) keeps talking only to control planes, never to
  Tauri IPC; the shell's sidecar daemon simply becomes the first entry
  in the connection list. Connection registry, per-runtime tokens, and
  the stale-cache live in the UI layer.
