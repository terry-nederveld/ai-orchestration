# Context

v1 routing profiles (orchestrator routing table) map a step's role to an
executor id, model, and system prompt — nothing more. Phase 2 needs full
reusable execution configurations: provider/model, fallback behavior,
instruction and context policy, tools, permissions, and budget — shared
across many workflows, versioned like every other definition (ADR-0018),
and stable for the lifetime of a durable run. Provider outages during a
days-long run must not strand it, but which model executes must never be
a runtime surprise (mission §19).

# Decision

1. **Profiles compose from fragments; they never inherit.** An
   `AgentProfileDefinition` names an ordered `compose` list of other
   profile definitions plus its own fragment. `composeProfile` applies
   fragments in declared order — listed fragments first, the profile's
   own fragment last, call-site overrides after that. Merge rules are
   fixed per field: scalars (primary selection, fallback policy, budget,
   traversal, attachments, maxTurns, timeoutMs) are last-writer-wins;
   `systemPrompt` concatenates in order; `toolNames` unions;
   `permissions` concatenate. The resolved profile records
   `composedFrom` (fragment names in application order) for provenance.
   A profile that resolves to no primary selection is a composition
   error, not a runtime default.
2. **Profiles resolve from the pinned snapshot, never live definitions.**
   `resolveProfileFromSnapshot` looks up the profile and, recursively,
   every composed fragment in the run's ResolvedSnapshot. A run that
   started under profile version N keeps executing under N across
   suspensions and resumes; edits affect only future runs (ADR-0018).
3. **Fallback is a deterministic ordered chain.** A `FallbackPolicy`
   declares an ordered list of alternative `ModelSelection`s after the
   primary and a trigger: `outage-only` engages the chain only on
   provider outages and rate limits; `any-failure` additionally engages
   on fatal model errors (a FATAL_FAILURE outcome or thrown executor
   error). The default is `outage-only`, so a model's own hard failure
   surfaces rather than being silently retried elsewhere. Every fallback
   selection must still satisfy the policy's `minimumCapabilities`,
   checked at resolution. The engine walks the chain strictly in order;
   when it is exhausted the node fails with the last error.

# Rationale

- Composition with explicit per-field merge rules keeps "what will this
  agent run with" answerable by reading the fragments in order —
  inheritance hierarchies make the same question require whole-tree
  reasoning and invite diamond conflicts.
- Distinguishing outage-only from any-failure fallback separates
  availability engineering (keep the run alive through an outage) from
  quality masking (paper over a model that cannot do the work); the
  latter must be an explicit author choice.
- Snapshot resolution makes profile behavior a run invariant, which the
  execution specification and judgment records depend on for audit.

# Alternatives Considered

- **Profile inheritance (extends chains)** — override semantics become
  position-dependent across a tree rather than a list; rejected for
  ordered composition.
- **Nondeterministic or load-balanced model choice** (pick any healthy
  provider, cheapest-suitable auto-routing) — destroys reproducibility
  and makes run behavior unexplainable after the fact; rejected. The
  capability data exists; any future automatic routing must compile to a
  declared deterministic chain first.
- **Fallback decided per-call by the agent runtime** — hides policy in
  adapter code; rejected in favor of policy declared on the profile and
  executed by the orchestrator.

# Consequences

- Positive: one profile serves many workflows; outages degrade along a
  path the author chose; `composedFrom` plus the snapshot answers
  exactly which configuration produced any given session.
- Negative: permissions only accumulate through composition — a fragment
  cannot subtract a rule added earlier, so narrow profiles must be built
  from narrow fragments; fragment ordering is semantic and the designer
  must surface it.
- Fallback re-issues the whole agent call on the next selection; partial
  work from a failed primary attempt is not carried over (checkpoints,
  ADR-0020, bound the loss).

# Implementation Notes

- Types and `composeProfile` in `@overture/core` (profiles.ts);
  snapshot resolution and the chain walk in `@overture/orchestrator`
  (graph/node-executors.ts: `resolveProfileFromSnapshot`, `runAgent`).
  Outages are recognized by error category (`provider-outage`,
  `rate-limit`).
- The v1 routing table (routing.ts) remains for the v1 engine only;
  graph runs resolve exclusively through snapshot-pinned profiles.
