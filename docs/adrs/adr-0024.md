# Context

When a work item is discovered, something must decide which workflow —
if any — runs it. v1 answers with first-match auto-run: the first
workflow whose trigger and eligibility accept the item starts
(`selectWorkflow` in the orchestrator's eligibility module). With one
workflow that is fine; with a catalog of workflows and templates it is a
silent guess, and a wrong guess spends budget, claims the item, and may
touch external systems before anyone notices. Meanwhile the selections
humans do make are a signal the system currently discards.

# Decision

1. **Match cardinality decides the behavior.** Trigger and eligibility
   evaluation stays pure and deterministic over the canonical WorkItem;
   what changes is what happens with the result set:
   - *Zero matches* — no action. The item stays untouched; discovery
     may surface it as unrouted, but nothing runs and nothing is
     claimed.
   - *Exactly one match* — eligible for auto-start where the lane or
     configuration opts in; otherwise it is offered, not started.
   - *Multiple matches* — never a guess. The item enters a durable
     `WORKFLOW_SELECTION_REQUIRED` state backed by a single-choice
     human-input wait (ADR-0019) whose choices are the matching
     workflows. The selection satisfies the wait and starts the chosen
     workflow; until then nothing executes.
2. **Observed selections may become suggested rules — never silent
   rules.** Resolved selections are recorded (item characteristics →
   chosen workflow). When a pattern recurs, the system may generate a
   rule *suggestion* — a candidate trigger/eligibility refinement that
   would have disambiguated those items — presented with its supporting
   observations. A suggestion persists as an actual routing rule only
   through explicit human approval, which creates a new definition
   version (ADR-0018). Rejected or ignored suggestions change nothing.
3. **No auto-applied heuristics.** Confidence thresholds, similarity
   scores, or model judgment never route an item by themselves. The
   routing table a run consults is always human-approved declarative
   configuration, so "why did this workflow run" always has a
   deterministic, inspectable answer.

# Rationale

- Starting an autonomous workflow is an expensive, partially external
  side effect; on ambiguity the cheap and reversible action is to ask.
  The durable wait machinery makes asking free — the question survives
  restarts and costs nothing while open.
- Routing through approved declarative rules keeps eligibility
  evaluation auditable and testable as pure functions; learning changes
  the rules through the same versioned, approved path as any other
  definition edit, so the audit trail is uniform.
- Recording selections separately from applying them lets suggestion
  quality improve without any behavioral risk in the meantime.

# Alternatives Considered

- **Keep first-match auto-run** — order-dependent silent guessing;
  rejected as the v1 defect this decision exists to fix.
- **Model-scored best-match routing** — nondeterministic, unexplainable
  after the fact, and wrong exactly on the ambiguous cases that matter;
  rejected.
- **Auto-apply learned rules above a confidence threshold** — converts
  a statistical hunch into unattended external side effects; rejected.
  The threshold may gate when a *suggestion* is raised, never when a
  rule takes effect.
- **Priority numbers on workflows to break ties** — hides ambiguity
  instead of resolving it, and decays as the catalog grows; rejected.

# Consequences

- Positive: no run ever starts on a guess; every routing decision is
  reproducible from versioned rules; the Needs You surface gains a
  well-defined "choose a workflow" item backed by the standard wait
  machinery rather than a bespoke inbox.
- Negative: ambiguous items wait on a human — that is the point, but
  overlapping trigger definitions will generate selection requests until
  rules are refined; suggestion generation adds a storage and review
  surface that is only worth it if suggestions are good enough to
  approve.
- Auto-start on a single match remains opt-in, so a fresh install is
  ask-first by default.

# Implementation Notes

- Trigger/eligibility evaluation stays in `@overture/orchestrator`
  (eligibility.ts) as pure functions; the selection wait reuses
  `single-choice` HumanInputRequestSpec and WaitCondition
  (`@overture/core` graph.ts, waits.ts). Selection records, suggestion
  generation, and the approval flow persist via `@overture/persistence`;
  approved rules write new workflow-definition versions through the
  definition store (ADR-0018). Note the orchestrator's routing.ts is
  the v1 agent-executor router and is unrelated to this decision.
