# Context

Runs must wait minutes or days — for humans, approvals, time, external
events, dependencies, provider availability — without a live model session
and across daemon restarts. v1 has only an in-memory ApprovalBroker that
fails closed on timeout and a HUMAN_INPUT_REQUIRED terminal outcome;
restart recovery marks in-flight runs Failed. Model sessions must be
disposable: suspension has to release them and resumption has to work
without them.

# Decision

1. **WaitCondition.** One persisted abstraction covers every wait:
   `{ id, runId, nodeId, kind, parameters, createdAt, satisfiedAt?,
   satisfaction? }` with kinds `human-input`, `approval`, `time`,
   `external-event`, `dependency`, `provider-availability`,
   `work-item-event`. A node that yields a wait causes the engine tick to
   persist the condition and the run's checkpoint, transition the run to
   WAITING (or WAITING_FOR_HUMAN), release all model resources, and
   return. Satisfaction is an event: the WaitBroker matches incoming
   satisfactions (human responses, timer firings, provider events,
   work-item events) to open conditions and re-queues the run for a tick.
2. **Typed human input.** Human-input requests are typed — text, boolean,
   single choice, multiple choice, approval, secret, file/reference,
   free-form fallback — and declare their surface: `app`, `work_item`, or
   `both`. Every response, whatever the channel, normalizes into one
   `HumanInput` event `{ requestId, responder, at, value, channel }`.
3. **First valid response wins.** The first response that validates
   against the request's type satisfies the condition atomically
   (persisted compare-and-set); later responses are stored as
   supplemental context attached to the run, never applied to
   already-resumed execution. Promotion of supplemental context into a
   later spec revision is an explicit action. Default responder policy:
   any authorized user of the runtime; per-request narrowing is
   configuration.
4. **Timer waits** are satisfied by a persistent scheduler scan (due-time
   index), not in-process setTimeout, so they survive restarts.
5. **Secrets requested from humans** are written to the secret store and
   satisfied with the secret *name* — the value never enters run state,
   events, or context.

# Rationale

- One WaitCondition table with a broker is radically simpler than
  per-kind subsystems and gives the UI a single "what is everything
  waiting on" query — the Needs You surface falls out of it.
- First-response-wins with durable CAS resolves multi-responder races
  deterministically without locking humans out of adding later context.
- Normalizing work-item responses (comments, state changes, fields) into
  the same HumanInput event keeps providers as projection adapters
  rather than control-flow participants.

# Alternatives Considered

- **Blocking the engine tick on promises with long timeouts** — dies
  with the process; rejected (this is v1's failure mode).
- **Per-kind wait tables** — schema sprawl and N brokers; rejected.
- **Last-response-wins / merged responses** — non-deterministic resume
  semantics; rejected in favor of explicit context promotion.

# Consequences

- Positive: durable suspension becomes testable (kill the daemon while
  WAITING, restart, respond, resume — an acceptance requirement);
  approvals stop being fail-closed timeouts and become real state.
- Negative: every waitable interaction needs request/response schema
  discipline; the v1 ApprovalBroker is superseded and its API surface
  (approvals list/resolve) is re-implemented over WaitConditions.

# Implementation Notes

- Types in `@overture/core` (waits.ts); WaitBroker + repositories in
  `@overture/persistence` and orchestration wiring in
  `@overture/orchestrator`; control-plane endpoints replace the
  approval endpoints with generic wait/respond endpoints while keeping
  approval routes as sugar.
