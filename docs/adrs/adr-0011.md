# Context

The product needs a desktop app, a CLI, and continuous background
orchestration that outlives any UI window. Docker Desktop and Ollama
demonstrate the dominant pattern: a long-running local daemon exposing a
loopback API, with GUI and CLI as thin clients of the same surface. This
also pre-positions the architecture for the future remote/team control
plane: the client/daemon seam is the local/remote seam.

# Decision

The orchestration core runs as a single long-lived Node daemon
(`overture daemon`) exposing:

- JSON-over-HTTP on `127.0.0.1:<port>` (default 43117, configurable),
- server-sent events for the event stream (UI timelines, logs),
- bearer-token auth using a per-install random token written 0600 to the
  local state directory (defense against other local users / browser
  CSRF-style requests to localhost).

The CLI talks only to this API (spawning the daemon on demand); the desktop
shell embeds/starts the same daemon as a sidecar process and renders the
same API. Nothing in the UI or CLI links against orchestration internals.

# Rationale

- One service layer means CLI and GUI cannot drift; headless operation is
  the default rather than an afterthought.
- Loopback HTTP + SSE is debuggable with curl, portable across platforms
  (no unix-socket/named-pipe divergence in v1), and maps directly onto a
  future remote deployment (same API over TLS with real auth).
- Research confirmed this is the pattern used by comparable products
  (Docker Desktop daemon + clients; Ollama's 127.0.0.1:11434 API).

# Alternatives Considered

- **Unix socket / named pipe** — stronger local isolation but two platform
  code paths and worse debuggability; the loopback + token approach gets
  comparable protection with one path. Revisitable without API changes.
- **gRPC** — used by Docker internally between daemons, but its clients are
  heavier and the streaming benefit over SSE is marginal here.
- **In-process orchestration inside the desktop app** — no headless mode,
  orchestration dies with the window; rejected outright.

# Consequences

- Positive: headless-first; UI framework becomes a swappable shell; remote
  control plane is an adapter change, not a redesign.
- Negative: daemon lifecycle management (start, health, shutdown) is our
  code to own; the auth token file must be protected (0600) and never
  logged.

# Implementation Notes

- packages/server (daemon + HTTP API), packages/cli (client), desktop shell
  starts the daemon as a sidecar (ADR-0012).
