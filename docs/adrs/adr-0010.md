# Context

Local persistence must cover runs, sessions, an append-only event log,
claims, usage, and configuration; survive restarts; require zero setup; and
package cleanly into a desktop app on three platforms. Native npm modules
(better-sqlite3) historically complicate cross-platform packaging (ABI
rebuilds per Electron/Node version).

# Decision

Use Node's built-in `node:sqlite` (DatabaseSync) behind the
`PersistenceProvider` port, with numbered idempotent SQL migrations. Claim
atomicity is a single conditional `INSERT … ON CONFLICT DO UPDATE … WHERE`
statement. JSON columns hold aggregates that nothing queries relationally
(run history, session messages, usage). An in-memory Map-backed provider
implements the same port for tests; a server database can replace the
adapter later without domain changes.

# Rationale

- Zero native dependencies: nothing to rebuild per platform or shell —
  verified working on Node 26 including transactions and conditional
  upserts.
- SQLite's single-file durability fits a per-user local daemon exactly.
- The repository-port boundary was proven by running one behavioral
  contract suite against SQLite (file), SQLite (:memory:), and the
  in-memory provider.

# Alternatives Considered

- **better-sqlite3** — richer API, but a native dependency with packaging
  cost and no needed capability beyond node:sqlite; rejected.
- **Plain JSON/JSONL files** — no atomic claims, no indexed event queries.
- **Embedded Postgres** — absurd overhead for one machine.

# Consequences

- Positive: clean packaging; atomic claims; contract-tested replaceability.
- Negative: DatabaseSync is synchronous — acceptable for a low-write local
  daemon; a server deployment would swap the adapter (the port is async).

# Implementation Notes

- packages/persistence; migrations in migrations.ts; events use an
  autoincrement `seq` so `afterEventId` cursors are well-defined.
