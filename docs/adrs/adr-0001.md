# Context

Overture integrates many external systems whose official SDKs and tooling are
strongest in specific ecosystems: the Claude Agent SDK (TypeScript/Python),
the MCP official SDK (TypeScript first), Octokit for GitHub, the Linear SDK
(TypeScript), Anthropic/OpenAI SDKs (TypeScript first-class). The product also
needs a desktop UI, which will be web-technology based regardless of shell
choice, and a CLI. The core must be testable, portable across macOS, Windows,
and Linux, and hospitable to contributors.

Local environment realities also matter: coding-agent CLIs (`claude`,
`codex`, `gh`) are external processes, so the core language must excel at
process orchestration and async I/O rather than raw compute.

# Decision

Implement the orchestration core, providers, CLI, and control plane in
TypeScript (strict mode) running on Node.js ≥ 22, as ESM modules.

# Rationale

- Every provider we must integrate ships a first-class TypeScript SDK; no
  other language covers all of them.
- One language across core, CLI, control plane, and UI removes an entire
  class of contract-drift bugs and halves the toolchain surface.
- The workload is async I/O and subprocess orchestration — Node's strength.
- Node ≥ 22 ships `node:sqlite`, WHATWG streams, `AbortSignal` combinators,
  and stable test/tooling support, reducing native-dependency risk.
- Strict TypeScript with branded identifiers gives enough type rigor for the
  domain model without a rewrite-level investment in another language.

# Alternatives Considered

- **Rust end-to-end** — strongest runtime and packaging story (single
  binary), but no official Claude Agent SDK, immature MCP client options at
  the time of decision, and materially slower iteration for a product this
  broad. Rust remains in play for the desktop shell (Tauri).
- **Go** — good daemon story, but the same SDK-coverage gap plus a separate
  language from the inevitable web UI.
- **Python** — good SDK coverage, but weak desktop packaging, heavier
  process model, and a worse story for shipping a self-contained app to
  non-developers.

# Consequences

- Positive: fastest possible provider integration; shared types between
  daemon, CLI, and UI; single test framework; contributors need one stack.
- Negative: Node runtime must be shipped with the desktop app (sidecar) —
  this constrains the packaging design (see the desktop-framework ADR).
- Risk: CPU-heavy workloads would need worker threads; none are on the
  roadmap (model inference is remote or delegated to local servers).

# Implementation Notes

- `tsconfig.base.json` enforces `strict`, `exactOptionalPropertyTypes`,
  `noUncheckedIndexedAccess`, ESM `NodeNext` resolution.
- Prefer built-in Node APIs (`node:sqlite`, `node:child_process`, `fetch`)
  over native npm dependencies to keep cross-platform packaging simple.
