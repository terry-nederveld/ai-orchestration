# Context

OpenAI Symphony (github.com/openai/symphony, Apache 2.0, spec SPEC.md) is the
closest prior art: it turns Linear/GitHub issues into isolated Codex runs via
a discover → claim → execute → deliver lifecycle, an atomic in-memory claim
set, per-issue sanitized workspaces, and tracker reconciliation on every poll.
Its limitations are also instructive: all claim/retry state is in-memory (lost
on crash), a single tracker/agent pairing, and no orchestrator-level write
API (agents mutate the tracker through host-side tools).

# Decision

Adopt Symphony's lifecycle shape, generalized and hardened:

- Lifecycle: discover → evaluate (trigger + eligibility) → claim → prepare
  workspace → execute workflow → verify/review (workflow steps) → deliver →
  transition work item → cleanup.
- Claiming is two-layer: the authoritative claim is an atomic `tryClaim` in
  the persistence layer (SQLite conditional upsert, survives restarts); the
  work-provider claim (assignee/label) is a best-effort visibility marker.
- Restart recovery: non-terminal runs found at startup are marked FAILED
  with an interruption reason and their claims released; re-queueing is
  explicit, never silent.
- The scheduler is a single-authority instance (no distributed consensus in
  v1), with bounded run concurrency.
- Work-item mutation happens through the orchestrator's provider adapters
  (transition/comment actions), keeping tracker credentials out of agent
  sandboxes — same credential-isolation stance as Symphony, but with the
  orchestrator (not agent tools) owning delivery.

# Rationale

- Symphony demonstrates the lifecycle works; its in-memory claim weakness is
  precisely what our persisted ClaimStore fixes (crash cannot double-run or
  orphan work invisibly).
- Keeping single-authority scheduling avoids distributed locking while the
  ClaimStore interface still permits a server-backed implementation later.

# Alternatives Considered

- **In-memory claims + re-derive from tracker on restart (Symphony)** —
  simpler, but loses retry state and makes "was this already attempted?"
  unanswerable locally; rejected.
- **Distributed lock service now** — premature enterprise complexity.
- **Agent-driven tracker writes (Symphony's model)** — flexible but makes
  delivery behavior prompt-dependent; we prefer deterministic workflow
  actions for state transitions, with agents able to comment via tools when
  explicitly granted.

# Consequences

- Positive: idempotent claiming under crash/restart; auditable run history;
  work items never processed concurrently by two runs of one instance.
- Negative: two orchestrator instances sharing a work source can still race
  at the external-marker level; multi-instance coordination is deferred to a
  shared ClaimStore implementation (documented post-v1).

# Implementation Notes

- packages/orchestrator (Scheduler, RunCoordinator), packages/persistence
  (ClaimStore).
- Workspace naming: slugified identifiers with traversal-safe resolution
  (packages/workspaces/src/path-safety.ts), mirroring Symphony's sanitized
  workspace keys.
