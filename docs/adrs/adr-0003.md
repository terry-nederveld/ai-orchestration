# Context

Overture must swap any of: model provider, coding-agent provider, work
tracker, source-control platform, workspace strategy, secret store,
persistence, and workflow definitions — without touching orchestration
logic. Provider capabilities differ (streaming, tool use, subagents, session
resume), and new providers will appear that we cannot anticipate. The failure
mode to avoid is `if (provider === 'github')` branching spread through the
codebase.

# Decision

Adopt a hexagonal (ports-and-adapters) architecture centered on
`@overture/core`, which contains only:

- the canonical domain model (WorkItem, Run, Workspace, Budget, events, …)
- provider port interfaces (`ModelProvider`, `AgentProvider`, `WorkProvider`,
  `SourceControlProvider`, `WorkspaceProvider`, `SecretProvider`,
  `PersistenceProvider`, `NotificationProvider`, `ToolProvider`,
  `ExtensionProvider`, `WorkflowProvider`, `EventBus`)
- pure domain logic (state machines, budget accounting, capability sets)

Vendor-specific code lives exclusively in adapter packages. Providers
advertise a `CapabilitySet`; orchestration code asks
`capabilities().has(Capability.ToolUse)` and never inspects provider ids for
behavioral decisions. Two distinct provider concepts are kept separate:
**ModelProvider** (direct inference) and **AgentProvider** (an external
agent runtime owning its own loop); the native runtime satisfies the same
operational contract as an external agent provider, so the orchestrator
treats all executors uniformly.

# Rationale

- Interchangeability is the product's core promise; only enforced ports
  deliver it.
- Capability negotiation lets the router select providers by requirement
  (tool use, vision, resume) instead of hardcoded names, which is also the
  path to automatic cheapest-suitable-model routing.
- Separating model and agent providers reflects real economics (API tokens
  vs subscription seats) and real control differences (our loop vs theirs).

# Alternatives Considered

- **Feature flags / conditionals per vendor** — fastest short-term, decays
  into unmaintainable branching; rejected.
- **Plugin-only architecture (everything dynamically loaded)** — maximal
  flexibility but heavy for first-party adapters; instead, first-party
  adapters are ordinary packages implementing the same ports that the
  extension system will use.
- **Single "Provider" interface with optional methods** — collapses two
  genuinely different lifecycles (stateless inference vs long-running agent
  sessions) into one contract; rejected for clarity.

# Consequences

- Positive: adding a provider means implementing one interface and passing
  its contract test suite; nothing in the kernel changes.
- Positive: deterministic fakes implement the same ports, enabling full
  orchestration tests with zero network access.
- Negative: some provider-unique features are not expressible through the
  neutral ports and must be exposed via `metadata`/extensions; this is the
  accepted cost of neutrality.

# Implementation Notes

- `@overture/core` must remain dependency-free.
- Adapters never leak vendor SDK types across their package boundary.
- Every port gets a reusable contract test suite in `@overture/testkit`
  that all implementations — fake and real — must pass.
