# Context

Phase 2 gives workflows a visual designer. The risk with designers is a
privileged format: a UI-only representation that drifts from what files
and the engine actually execute, until "what the designer shows" and
"what will run" are different questions. The second question the
designer must answer — "what would happen if this ran on that item?" —
is today answerable only by running it, which claims items, starts
sessions, and spends budget.

# Decision

1. **One canonical graph document; the designer is just an editor.**
   Designer edits produce the same canonical `WorkflowGraph` document
   (typed nodes, declared transitions, joins, guards, effects,
   projection — ADR-0017) that YAML authoring compiles into and that
   the definition store versions (ADR-0018). YAML → graph → designer →
   graph round-trips losslessly; there is no designer-private schema,
   and anything the designer cannot represent is a designer gap, not a
   second format. Layout hints, if stored, are cosmetic metadata with
   no execution semantics.
2. **Validation is shared, not duplicated.** The designer surfaces the
   same structural validation the engine enforces (`validateGraph`:
   referential integrity, reachability, terminal coverage, the
   bounded-cycle rule, join restrictions) as live feedback, so a graph
   the designer accepts is a graph the engine accepts.
3. **Lifecycle gates activation.** Definitions edited in the designer
   follow the DRAFT / ENABLED / DISABLED lifecycle (ADR-0018): saving
   creates versions freely, but only an explicitly ENABLED version is
   eligible to serve new runs. The designer always makes clear that
   editing mints a new version and never touches in-flight runs.
4. **Evaluate is the designer's dry-run, side-effect-free by
   construction.** Evaluate answers "what would this workflow do with
   this work item right now" without running anything:
   - It executes against *read-only ports only* — it may inspect the
     item, repositories, definitions, and capability registrations, but
     it is wired with no port that can write, so a side effect is a
     type error, not a tested-for behavior.
   - Node outputs are *hypothetical*: for each decision point the user
     (or a default) supplies assumed structured outputs, and Evaluate
     walks the determinable path — evaluating real transition
     conditions, guards, and joins against the assumptions — reporting
     where the walk becomes undeterminable rather than pretending.
   - Expected side effects (commits, comments, item transitions,
     projections, child runs) are *described* at the point they would
     occur, never executed.
   - The report enumerates *blockers*: everything that would prevent a
     real start — failed eligibility, missing capabilities or
     providers, unresolved repositories or secrets, disabled
     definitions — so "why won't this run" is answered before anyone
     tries.

# Rationale

- A single canonical document is the same determinism argument as
  ADR-0017 applied to authoring: whatever surface wrote the graph, the
  engine executes one artifact, and Evaluate/audit reason about that
  artifact.
- Making Evaluate side-effect-free by construction (absent write ports)
  rather than by policy means no code path, present or future, can leak
  an effect from a dry-run — the guarantee survives refactoring.
- Hypothetical-outputs walking is honest about what a dry-run can know:
  agent behavior is assumed, engine behavior (conditions, joins,
  bounds, effects) is computed exactly, because the engine — not the
  model — owns those decisions.

# Alternatives Considered

- **A designer-native format compiled to the graph** — the drift
  machine this decision forbids; rejected.
- **Evaluate as a sandboxed real run** (mocked providers, real agents)
  — expensive, slow, nondeterministic, and still capable of leaking
  effects through any imperfect mock; rejected as the default (it can
  exist later as an explicit "rehearse" action, distinct from
  Evaluate).
- **Model-predicted outcomes in Evaluate** — replaces exact engine
  semantics with a guess about a guess; rejected: assumptions are
  user-supplied and labeled.
- **Designer edits mutating the enabled version in place** — breaks the
  ADR-0018 immutability contract; rejected.

# Consequences

- Positive: files, API, and designer converge on one reviewable
  artifact; Evaluate makes workflow authoring test-first (blockers and
  paths visible before any run) and doubles as the run-preview surface
  for routing decisions (ADR-0024).
- Negative: the designer must faithfully render every graph feature or
  clearly mark unsupported constructs read-only — partial rendering
  that silently drops features would reintroduce drift through the
  back door; Evaluate's usefulness degrades on graphs whose branching
  depends heavily on assumed outputs, and the report must say so
  rather than overstate confidence.
- Hypothetical walks cannot bound what a real agent will actually
  produce; Evaluate verifies structure and wiring, not model quality.

# Implementation Notes

- Canonical model and shared validation in `@overture/core` (graph.ts,
  graph-validate.ts); YAML compilation in `@overture/workflow`
  (graph-engine/compile.ts); versioning/lifecycle via the definition
  store (ADR-0018). The Evaluate walker lands beside the coordinator in
  `@overture/orchestrator` (graph/), constructed with read-only port
  views; the designer UI lives in the desktop app and talks to Evaluate
  through the control plane.
