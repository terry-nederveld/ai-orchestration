# Context

v1 consumes work through a single scheduler loop: discover, claim, run,
with concurrency as one global number. Phase 2 orchestrates several kinds
of work against the same backlog — a serial delivery pipeline here, a
parallel triage lane there, a nightly discovery run — each with its own
ordering discipline, WIP limits, capability constraints, and budget
(mission §22–§23). Recurring work must fire on schedule without a
long-lived in-process timer, because the daemon restarts.

# Decision

1. **Lanes.** A `LaneDefinition` binds a work source (with optional
   query overrides) to a workflow route, with a consumption policy, a
   `maxActive` cap on simultaneously active runs, optional capability
   and profile constraints on who may serve the lane, an optional
   budget, and an enabled flag. Lanes are versioned definitions like
   everything else (ADR-0018). The backlog's native rank is the
   canonical priority; lanes never invent an ordering of their own.
2. **Three consumption policies**, differing only in what happens when
   the ranked head cannot start:
   - `strict_serial` — one item at a time in rank order; a blocked head
     halts the lane until it unblocks. Order is the guarantee.
   - `skip_blocked` — rank order, but a blocked item is skipped with an
     emitted event recording what was skipped and why; the lane keeps
     moving. Progress is the guarantee, visibly.
   - `ranked_parallel` — fill up to `maxActive` in rank order; as runs
     finish, the next eligible items by rank take their place.
3. **Recurring schedules are persisted firings, not timers.** A
   `ScheduleDefinition` carries a 5-field cron expression (minute
   precision), the workflow to start, and an optional synthetic payload
   for runs with no external work item. The scheduler computes due
   firings by comparing the cron line against the persisted last firing
   (`ScheduleRepository.lastFiring` / `recordFiring`, keyed by schedule
   name with due and fired times and the started run id): a restart
   re-derives what is due from storage, so a schedule never double-fires
   and a missed window is detectable rather than silently lost.
4. **All time is injected.** Lane evaluation and schedule due-ness read
   the ambient `Clock` port, never `Date.now()` directly — scheduling
   decisions are unit-testable and reproducible.

# Rationale

- Treating the backlog's own rank as canonical keeps prioritization
  where humans already do it (the tracker), instead of a second
  ordering that drifts from it; policies only decide how strictly rank
  converts into dispatch order.
- The three policies cover the real disciplines observed in delivery
  work (strict pipelines, keep-moving triage, bounded parallel fan-out)
  without a policy plugin surface nobody asked for.
- Persisted firings make recurrence idempotent across restarts by the
  same argument that made waits durable (ADR-0019): derived-from-storage
  beats remembered-in-process.

# Alternatives Considered

- **Per-lane priority expressions** — a second source of ordering truth
  competing with the tracker's rank; rejected.
- **In-process cron timers** — lost on restart, double-fire on overlap
  between old and new processes; rejected for the persisted-firing scan.
- **One global run queue with weights** — cannot express "this lane is
  strictly serial while that one runs three wide"; rejected.

# Consequences

- Positive: WIP limits, ordering discipline, and budget become explicit
  lane configuration; skip events give an audit trail for every item
  passed over; restarts are safe by construction for recurrence.
- Negative: `strict_serial` willingly accepts head-of-line blocking —
  that is its contract, and operators must pick `skip_blocked` when they
  do not want it; cron is minute-granular by design, and sub-minute
  recurrence is out of scope.
- Multiple lanes may match the same item; claim semantics (the kernel
  ClaimStore) remain the arbiter, so lanes contend rather than
  duplicate.

# Implementation Notes

- Types in `@overture/core` (lanes.ts: `LaneDefinition`,
  `ConsumptionPolicy`, `ScheduleDefinition`, `ScheduleRepository`);
  firing persistence in `@overture/persistence` (schedule-repository).
  The graph-aware lane scheduler lands in `@overture/orchestrator`,
  replacing the v1 single-loop scheduler for lane-managed sources.
