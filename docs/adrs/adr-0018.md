# Context

Phase 2 introduces many kinds of reusable definitions — workflows,
sub-workflows, gate sets, rubrics, agent profiles, templates, mapping
rules — that evolve over time while long-lived runs (days of waiting) must
behave exactly as they did when they started. v1 definitions are
unversioned files resolved at execution time: editing a workflow while a
run waits would change its behavior on resume.

# Decision

1. **DefinitionVersion.** Every definition kind is stored as an immutable
   versioned document: `{ kind, name, version, contentHash, document,
   createdAt }`. The version is a monotonically increasing integer per
   (kind, name); the contentHash (SHA-256 of the canonicalized document)
   deduplicates — saving an unchanged document returns the existing
   version instead of minting a new one. Documents are canonical JSON of
   the parsed definition, not raw YAML, so formatting changes do not
   create versions.
2. **ResolvedSnapshot.** When a run starts, the engine resolves the root
   workflow and everything reachable from it — sub-workflows, gate sets,
   rubrics, agent profiles, policies — into one immutable snapshot pinned
   to exact versions, stored once (content-addressed) and referenced by
   the run. Ticks and resumes execute exclusively against the snapshot;
   later edits create new versions that affect only future runs.
3. **Lifecycle.** Definitions carry DRAFT / ENABLED / DISABLED lifecycle
   independent of versioning; only ENABLED definitions are eligible for
   new runs, but a pinned snapshot keeps executing even if its source is
   later disabled (cancellation is an explicit operator action, never a
   side effect of editing).
4. Rubric and gate-set versions follow the same rule with one addition:
   evaluation-time mutation is impossible by construction — the evaluating
   node reads criteria from the snapshot, and outcome-driven improvement
   proposals create new versions only through explicit approval.

# Rationale

- Content addressing gives cheap, automatic versioning with no manual
  bump ceremony and structurally guarantees snapshot immutability.
- One snapshot per run (rather than per-definition pins scattered across
  tables) makes resume, Evaluate, and audit trivially consistent: the
  question "what exactly is this run executing?" has one answer.

# Alternatives Considered

- **Semantic versions authored by hand** — ceremony, drift, and nothing
  enforces that "1.2.0" content actually differs; rejected as the
  primary mechanism (names/labels may still be layered on later).
- **Git as the definition store** — attractive for repo-level workflow
  files, but definitions also come from the UI/designer and must version
  uniformly across sources; repo files are ingested into the same store
  with provenance instead.
- **Pin-by-reference (store version numbers only)** — leaves resume
  correctness dependent on the store never losing rows; embedding the
  resolved documents in the snapshot makes runs self-contained.

# Consequences

- Positive: reproducible runs, safe editing, exact Evaluate, honest
  history for judgment observability.
- Negative: storage grows with versions (mitigated by content-hash
  dedup and canonicalization); the designer must surface "you are
  editing a new version" clearly.

# Implementation Notes

- Types in `@overture/core` (definitions.ts); store port + SQLite
  implementation in `@overture/persistence`; canonicalization =
  stable-key-ordered JSON.
