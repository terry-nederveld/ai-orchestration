# Context

Durable runs outlive model sessions, daemon processes, and the assumptions
they started with: repositories change, work items are edited, humans add
context while a run waits. Something immutable must record what a run was
doing and under which inputs — and something durable must hold the work
product itself, because sessions are disposable (mission §6–§7).

# Decision

1. **ExecutionSpecification.** Every run carries an immutable, revisioned
   specification: goal, acceptance criteria, work item and related items,
   resolved repositories with roles and provenance, discovered
   instructions (path + content hash + whether applied), promoted human
   context, pinned snapshot id, profile, and completion criteria.
   Revision 1 is created at start. On resume, the orchestrator re-inspects
   authoritative sources (work item, instruction files, repositories),
   builds a candidate spec, and creates revision N+1 only when materially
   different (`specsMateriallyDiffer`); history is append-only. Provider
   session continuation is an optimization — resume correctness depends
   only on the spec, the snapshot, and the checkpoint.
2. **Checkpoint strategies are domain-appropriate ports.**
   - *Coding work*: the durable product is a remote git branch. Every
     coding run owns one; before suspension the strategy commits
     meaningful changes as a conventional `chore(checkpoint)` commit and
     pushes. Restore recreates a fresh worktree from the remote branch —
     a replacement session never depends on the old workspace.
   - *Ideation/requirements work*: the durable product is the originating
     work item. A delimited managed section in the body holds the current
     machine-maintained summary; all human content outside the delimiters
     is preserved byte-for-byte, and damaged delimiters cause refusal
     plus a comment, never overwrite. Comments carry events (paused,
     waiting, resumed, checkpoint summaries), not machine metadata.
   Checkpoints record strategy, coordinates (branch+sha or content hash),
   summary, and the spec revision they belong to.
3. Checkpoints are taken at wait boundaries (before suspension) and at
   strategy-meaningful moments; the WaitBroker refuses to suspend a
   coding run without a durable checkpoint unless the tree is clean.

# Rationale

- A pinned snapshot answers "what rules govern this run"; the spec
  answers "what exactly is it doing under those rules"; the checkpoint
  answers "where is the work". Keeping the three distinct keeps resume
  reasoning simple and auditable.
- Git and the work item are the two stores humans already trust and can
  inspect without Overture — the durable product is legible even if the
  orchestrator disappears.

# Alternatives Considered

- **Serializing model sessions as the durable artifact** — sessions are
  provider-specific, opaque, and unreplayable across providers; rejected
  as a correctness dependency (kept only as an optimization).
- **A single generic blob checkpoint** — hides the work product inside
  the orchestrator's database, invisible to humans and tools; rejected.
- **Mutating one spec row in place** — destroys the audit trail resume
  reconciliation depends on; rejected for append-only revisions.

# Consequences

- Positive: killing any session or the daemon during suspension loses
  nothing (acceptance scenarios A/B test exactly this); supplemental
  human input promotes into revisions explicitly rather than mutating
  history.
- Negative: checkpoint commits appear in branch history (conventional,
  squashable at merge); managed sections must be defended against
  concurrent human edits (last-writer refresh before every update).
